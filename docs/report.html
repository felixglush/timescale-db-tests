Compressing Bank Transactions

Does TimescaleDB make per-client statement queries over checking and Visa transactions faster or smaller, and does that change as the number of clients grows? We compared six storage layouts for the same data at 100, 1,000 and 10,000 clients.

Why compression is faster here

A statement query reads one client's rows for a date range. Its cost is mostly the number of 8 KB pages Postgres has to read. On a cold cache, every page is a disk read.

Transactions arrive in time order, interleaved across all clients, so an ordinary table stores them that way. At 10,000 clients, the roughly 73 rows on one page belong to about 73 different clients. One client's month of 95 transactions ends up on about 95 different pages. Compression rewrites each closed chunk grouped by client_id, so the same month becomes a single compressed batch that spans one or two pages.

Two effects stack up. Locality: a client's rows are adjacent, so a query reads a few pages instead of one page per row. Size: the batches are 3 to 4 times smaller than the rows they replace. Locality is the bigger effect. A plain table physically re-sorted by (client_id, txn_ts) (plain_clustered) reads about as few pages as compression does, but it stays sorted only until new rows arrive. Compression re-applies the grouping to every chunk as its time window closes.

With everything already in memory there is no disk to save. Visiting about 95 cached pages costs about as much CPU as decompressing one batch, so the layouts tie on small queries. On a tiny table (100 clients, 19 MB), read-ahead pulls in neighbouring pages almost for free, and compression doesn't help either.

How TimescaleDB compression works

1 · chunk

Split by time

A hypertable stores rows in chunks, one per time window (7, 30 or 90 days here). Each chunk is compressed on its own.

2 · segment

Group and sort

Rows are grouped by segmentby = client_id, sorted by orderby = txn_ts, and cut into batches of up to 1,000 rows.

3 · pivot

One row per batch

Each batch becomes one row holding a compressed array per column, plus metadata: the client, the row count, and the first and last timestamps.

4 · encode

Lossless codecs

Delta-of-delta and bit packing for integers and timestamps, dictionaries for repeated values, and LZ-style compression for text. Every value comes back exactly as stored.

Queries read compressed chunks through an index on (client_id, first_txn_ts, last_txn_ts). It finds just the batches for the requested clients and date range, decompresses them, and then filters by date. The trade-off is CPU on read, and slower updates or inserts into chunks that are already compressed. The usual pattern is to compress a chunk once its window has closed.

Compressed bytes per row, by column

Measured on one chunk at 10,000 clients. Raw heap row ≈ 104 bytes.

Bigger chunks give each client more rows per batch: 22 at 7 days, 94 at 30 days, 282 at 90 days. More rows per batch means the per-batch overhead is shared more widely and the codecs have more to work with. The free-text description and the randomly timed txn_ts are what's left.

Findings

  1. Compression wins once data comes from disk, and the gap grows with the number of clients.At 10,000 clients with a cold cache, 90-day compressed chunks are 3.6 to 8 times faster than a plain table. Q4 reads 174 pages instead of 6,165.
  2. A hypertable on its own changes nothing for these queries.Its size and latency match a plain table. The (client_id, txn_ts) index already narrows the search, so splitting by time has nothing left to skip. Hypertables pay off for retention and fleet-wide time queries.
  3. With data in memory, the layouts are close.Q1 to Q3 take under 4 ms everywhere. Compressed is about 25% faster on the larger Q4.
  4. Locality does most of the work.A one-off CLUSTER reads as few pages as compression, but it decays as new rows arrive. Compression keeps the layout as data grows and shrinks it 4 times.
  5. Chunk interval is the main tuning knob.TimescaleDB's default of 7 days leaves about 22 rows per client batch: half the compression of 30 days, and the slowest compressed layout. 90 days was best on both size and speed.
  6. Bind client ids as integers.When a prepared statement received a smallint[] parameter, the cached plan couldn't use the compressed index and decompressed every client in the date range, about 6 times slower.

How it was measured

  • PostgreSQL with TimescaleDB in Docker, tuned for 4 GB and 4 CPUs, with JIT and parallel workers off. Host: 4 vCPU and 16 GB RAM.
  • Synthetic data: 3 purchases per client per day (60% Visa), payroll twice a month, and a monthly card payment, for 1,143 rows per client per year. Each client has one checking and one Visa account, plus vendors and categories.
  • Queries: Q1 is one client for one month. Q2 is one client for 1 to 12 months. Q3 is 10 clients for one month. Q4 is 10 clients for 1 to 12 months. Random parameters, the same sequence for every layout.
  • Warm: 200 runs per query after 20 warm-up runs. Cold: 25 runs per query, with caches emptied before each one. Times are server execution from EXPLAIN ANALYZE.
  • Limits: one connection and no concurrent inserts. 10,000 clients was the largest scale the disk could hold for six copies of the data.

Run history

Run 0smoke test

Fixed the Docker setup (the image's own init scripts and the PG18 data path) and checked that every layout uses the client and date index.

Run 1aborted

Masked account numbers collided at 10,000 clients, so I dropped the bad uniqueness constraint. Page counts were also being inflated by the join to accounts, so from run 2 on only the transactions scans are counted.

Run 2complete

Found that a smallint[] parameter disables the compressed index in cached plans. The benchmark now binds ids as integers.

Run 3cold biased

Caches were emptied only once per layout, so later queries reused cached pages. A code review flagged this.

Run 4reported

Caches are emptied before every cold query, and the run aborts if they can't be. Plain-table cold times roughly doubled while compressed barely moved, so the gap is larger than run 3 showed.
